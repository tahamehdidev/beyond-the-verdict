# Deviations from the proposal and from PLAN.md

Chronological log: where a later entry changes an earlier one it says so (earlier numbers marked 'superseded' are kept for the record). Entries are added when something differs from the approved proposal or the plan. After the `stp1-frozen` tag, any change to code, prompts or config must be logged here with the reason and a note on which results were rerun.

## Deviations from the approved proposal (pilot scope, decided before any result)
1. Pilot sample sizes (final, see Phase 3 notes 3 and 6): 400 tuning claims and a 750-claim pooled evaluation set (350 dev + 400 held-out train) instead of the proposal's 500 tuning and 1,500 evaluation. [Initially planned as about 250 / 350; superseded.] Reason: 2.5-day short-term assignment on a single 8 GB laptop GPU.
2. Tuning claims come only from train claims 0-999, because only `train_0_999.zip` (20.7 GB of 63.5 GB) of the train knowledge store was downloaded. Evaluation claims come from dev. Reason: time and download size. Consequence: tuning sample may not be representative of all train claims.
3. Date leakage control uses URL-embedded dates because the store records have no date field (see DESIGN_LOCK section 5).
4. Simulated verifiers, the C0-C2 interface, blind-labelled sets and the full A2/A3 ablations are not part of STP1.

## Phase 2 notes (13 Nov 2026)
1. **Retrieval implementation differs from `rank_bm25`.** `src/retrieve.py` implements sentence-level BM25 (k1=1.5, b=0.75, Lucene-style idf `ln(1+(N-df+0.5)/(df+0.5))`, always non-negative, no stop-word removal, no stemming) with postings built only for query terms. Reason: `rank_bm25.BM25Okapi` is too slow and memory-hungry for 3e5-1e6 sentences per claim. Difference: BM25Okapi floors negative idf at a fraction of the average idf; ours uses the always-positive variant. Verified against a brute-force reference of the documented formula in `tests/test_retrieve.py`; it was NOT compared numerically with `rank_bm25`. Speed on 3 real dev claims (326,980 / 1,009,165 / 911,416 sentences, 10 queries, k=5): 1.8 s / 4.9 s / 4.7 s retrieval plus 2.2 s / 6.1 s / 5.7 s to load and filter the store. Benchmark queries were the claim text and gold questions, for timing only; gold questions are never used by the pipeline.
2. **Information-value models use L2-regularised logistic regression (sklearn default C=1.0)** for both model A and model B, on logit(calibrated confidence) with state dummies (reference level Supports). The design lock says only "logistic regression". The CI resamples claims while holding out-of-fold predictions fixed (no refitting per resample).
3. **Isotonic calibration**: the calibrated confidence is the fitted isotonic map applied to the raw maximum probability (monotone); calibrated class probabilities (used for Brier) rescale the other classes proportionally. For temperature scaling the confidence is the maximum of the tempered probabilities.
4. **Cross-validation with rare classes**: the number of folds is reduced to the smallest class count (minimum 2) among classes with at least 2 members; singleton classes are placed in a dummy stratum for splitting only. The folds actually used are recorded by the caller.
5. Tests written and passing in Phase 2: state rules (exhaustive over all 441 count vectors x m in {1,2,3}), retrieval, classifier/calibration, metrics/policies/bootstrap/information value (synthetic data with known answers). (The LLM stages, the pipeline runner and the evaluation driver were written afterwards; see Phase 3 and Phase 3b notes.)

## Phase 3 notes (13 Nov 2026)
1. **Prompt versions.** v1 prompts ran on the 20 smoke claims first (results kept in `results/smoke_v1/`, cache entries kept). v1 problems found by reading outputs: 75% of answers Unverified, 5/20 claims all-Unverified, near-duplicate questions, and 74/200 questions containing the claim date. v2 prompts (`decompose_v2.txt`: questions must cover different angles, no date unless part of the claim; `answer_v2.txt`: "No" explicitly covers "not announced / not found / did not happen", Unverified only if the evidence does not address the question or disagrees) were chosen on NON-label criteria only: v2 gives Unverified 58% (v1 75%), all-Unverified claims 2/20 (5/20), near-duplicate pairs 2.6% (5.0%), dated questions 2/200 (74/200), Yes/No/Unverified 27/15/58% (v1 20/4/75%). Gold labels were not used to choose the prompt (20 claims are too few). Risk: v2 may be more willing to say Yes; the evaluation will show it. Prompt development used only tuning-pool claims; no dev (evaluation) claim has been run through the LLM.
2. **Latency bug fixed.** Answer calls took 2.3 s wall time while the server reported 0.13-0.24 s; cause was the client resolving `localhost` (IPv6 first). `model.host` is now `http://127.0.0.1:11434`. Smoke time per claim fell from 32.6 s to 13.4 s (decompose 6.8, retrieve 2.9, answer 3.6). Cache keys do not include the host, so v1/v2 cache records are unaffected.
3. **Sample sizes finalised from the speed test:** tuning 400 (S 107, R 242, C 21, N 30), evaluation 350 (R 200, S 94, N 28, C 28), smoke 20 (all 20 are inside the new tuning set, so their cached outputs are reused). The proposal's 500 / 1,500 is not reached. Tuning was raised from 250 to 400 to give the class-weighted classifier more Conflicting / Not-Enough-Evidence examples (13 and 19 before). Estimated LLM time: about 750 claims x 13.4 s = 2.8 h.
4. Smoke test gates (design plan: parse failures < 5%, first-attempt valid decompositions > 90%): v2 gave 0/200 answer parse failures and 20/20 valid first-attempt decompositions; 20/20 claims complete.
6. **Pilot evaluation set enlarged (decided before any evaluation output).** Added `eval_train`: 400 eligible train claims (index 0-999) not in the tuning sample (S 107, R 241, C 22, N 30), pooled with the 350 dev claims into a 750-claim primary evaluation set (C 50, N 58 versus 28 and 28 for dev alone). Reason: rare-class confidence intervals for the mechanism check would be too wide with dev alone. Cost: about 1.5 h more LLM time, and a mixed pool (dev claims are later in time), handled by reporting dev-only and train-held-out subsets next to the pooled result. Tuning, evaluation and smoke files from before this change were verified byte-identical after regenerating splits. Train claims 1000-3067 are reserved for the main project's final evaluation (see DESIGN_LOCK section 8).
7. (At the time of writing the full tuning and evaluation LLM runs were not done; they are logged below under Phase 3b and "Evaluation LLM runs".)

## Phase 3b notes (13 Nov 2026, during the tuning run)
1. **k-aware caching and counts.** Answer records now store `k`; `collect_counts` uses only answers for the configured k (records written before this field existed, i.e. the smoke runs, were all k=5 and are treated as such). `run_pipeline` gained `--k` (writes to `results/<split>_k<k>/`) and `--collect-only` (rebuilds counts.csv from the caches without any model call); counts.csv rows carry a `k` column. The tuning run for k=5 was launched after the k-aware change but before the `k` column and `--collect-only` were added, so its counts.csv is rebuilt with `--collect-only` once it finishes.
2. **Evaluation driver written and tested on synthetic data only** (`src/predict.py`, `src/run_eval.py`, `tests/test_run_eval.py`). It fits the classifier and calibrator on the tuning counts, applies them to the evaluation counts, and writes predictions, bootstrap tables and figures. A test flips every evaluation gold label and checks that verdicts, states and confidences do not change (evaluation labels are used only inside metrics). In `load_counts` the `gold` column is the class index 0..3 and `gold_label` the letter. The driver refuses to run unless `frozen: true`. It has not seen real pipeline output yet.
3. **Observed during the run:** per-claim time 8-17 s (mean about 11.6 s over the first 15 claims; retrieval time rises when other CPU work runs at the same time); GPU temperature 86-88 C at 94% utilisation with the laptop on a cooling pad.
4. **Tuning runs finished (13 Nov 2026).** k=5: 106 min, k=3: 76 min, k=8: 82 min (decompositions reused from the cache for k=3 and k=8). Each: 400/400 claims complete, 0 answer parse failures, 0 failed decompositions, 0 no-evidence answers. Unverified share of the 4,000 answers: k=3 73%, k=5 69%, k=8 66%. The k=5 counts.csv was rebuilt with `--collect-only` (k column present). ## Freeze (13 Nov 2026)
Chosen by `python -m src.tune --apply` on the 400 tuning claims only (scores in `results/tuning_selection/`): k=3, classifier gradient boosting (depth 3), m=2, calibration isotonic, tau=0.25. Rules exactly as DESIGN_LOCK section 4; calibration compared on cross-fitted confidences. Notes: (a) k=3 vs k=5 for logistic regression differ by 0.0001 macro-F1 (0.2438 vs 0.2437); the rule is applied literally, ties are not defined by a tolerance. (b) Tuning-set cross-validated performance is weak: macro-F1 0.24-0.28, accuracy 0.26-0.36 (majority-class accuracy 0.605; class-balanced training trades accuracy for macro-F1). The retrieval-limited, Unverified-heavy counts carry signal mainly for Supports (mean supporting answers 2.65 for S vs 1.85 for R). The pilot's headline numbers will therefore be modest, and the report says so. (c) State accuracy against the gold-derived state: m=1 0.195, m=2 0.240, m=3 0.218. config.yaml set to `frozen: true`; tag `stp1-frozen`.

## Post-freeze variant tests (tuning set only; no evaluation claim has been run)
Motivation (diagnostic on tuning data, 13 Nov 2026): 69-73% of answers are Unverified; 48% of tuning claims fall in the Insufficient state at m=2; only 11% of gold-Refutes claims get the Refutes state; k does not matter (AUROC of the supporting-minus-refuting margin 0.652 / 0.645 / 0.651 for k=3 / 5 / 8); the answerer was sometimes conservative when the snippets stated the answer.
Rule fixed BEFORE running (`src/compare_variants.py`): adopt a variant only if the mean-over-5-CV-repeats macro-F1 of the class-weighted logistic regression rises by >= 0.02 AND the Supports-vs-Refutes AUROC also rises, relative to the frozen setup, on the same 400 tuning claims. Otherwise the frozen setup stays. Every variant tried is listed here, adopted or not. The k grid is not redone for a variant (k=3 is kept); if a variant is adopted that is logged as a deviation, then `src.tune` is rerun, the config re-frozen and the tag moved.

   Result (42 min, 400/400 complete, 0 parse failures): NOT adopted. Answer mix Yes/No/Unverified 14/13/73% -> 17/24/60%. ## Post-freeze code fix and first evaluation (14 Nov 2026)
1. **Driver bug fix after the tag.** On its first run on real files `src.run_eval` stopped with a false k-mismatch error: `load_counts` reports k as a list of strings (`['3']`) and `main` compared it with the integer 3. Fixed in `src/run_eval.py` (compare with `[str(k)]`) and covered by `test_main_accepts_matching_k_and_rejects_mismatch`. The change is a guard only; it does not touch any model, state rule, metric or number. It is a code change after `stp1-frozen`, so it is listed here.

## Error analysis (14 Nov 2026)
`src/error_analysis.py` draws 8 unsafe errors of the baseline P0 per gold class (seeded, `seeds.bootstrap`; 32 cases of 186) plus 4 case-study cases (2 correct decisive verdicts kept by P3, 1 per gold class S and R; the 2 most confident unsafe errors that P3 did not withhold). `results/error_analysis/worksheet.md` shows claim, gold, counts, questions, answers and top snippet. Error types were assigned by hand while reading each case (`labels.csv`; summary `src/error_summary.py` -> `taxonomy_counts.csv`). Labels are a single-annotator draft (written with the assistant, who is not independent of the system's design); they should be reviewed by the author before being reported as "annotated", and no agreement statistic exists. Counts (n=32): evidence gap 11, claim nuance beyond six counts 8, answerer misread 4, classifier contradicts clear counts 3, decomposition 3, answerer conservative 1, polarity 1, gold hard to defend 1.
**Post-hoc diagnostic (not tuned, not part of the pre-set analysis; exploratory):** among the 263 claims with a decisive state (Supports or Refutes) the simple rule "Supports -> S, Refutes -> R" has accuracy 0.506 while the frozen class-weighted gradient-boosting verdict has 0.365, and the classifier agrees with the state on only 46.8% of them. Nothing was changed because of it; it indicates the forced-verdict baseline (balanced gradient boosting on six counts) is a weak baseline, which the report states.
